# Data model, persistence and secrets baseline

**Status:** architecture proposal; not an implemented database or deployed backend.
**Scope:** Android/mobile and Android TV first, with a portable domain model for later tablet, TV Box and other platform clients.

## 1. Current verified baseline

The current Flutter client persists data locally:
- playlist metadata in a JSON manifest under the app-private support directory;
- playlist source text in separate M3U8 files;
- active playlist selection in a text file;
- the legacy playlist and XMLTV guide in separate local files;
- favorites in SharedPreferences.

There is no verified server API, hosted database, account system, cloud synchronization service, payment service, or production credential configuration in the repository. Do not describe these as available features.

## 2. Data ownership and deployment decision

Use two persistence layers only when their use cases exist:

1. **On-device database (first implementation target):** SQLite via a maintained Flutter package, with schema migrations. It stores imported playlist metadata, normalized channels, favorites, guide data and user preferences. Keep the app usable offline.
2. **Optional remote service (later, only if accounts or multi-device sync are approved):** a documented HTTPS API backed by a relational database such as PostgreSQL. The server is authoritative for account, device and synchronization records. Never connect a public mobile client directly to a privileged database.

Do not choose a hosted vendor, create paid resources, or enable account registration until ownership, budget, privacy policy, data residency, operational support and account-recovery requirements are decided.

## 3. Logical entities

Use UUID/ULID identifiers generated by the owning layer. Persist timestamps in UTC (ISO-8601 at API boundaries). Store display timezone separately from event timestamps.

| Entity | Purpose | Important fields / constraints |
|---|---|---|
| user_account (future) | Optional sign-in identity | id, normalized_email, auth_provider, created_at, disabled_at; no plaintext password |
| user_profile (future) | User preferences | user_id, display_name, locale, timezone, created_at, updated_at |
| device (future) | Registered app installation | id, user_id, platform, app_version, device_label, last_seen_at, revoked_at; avoid hardware identifiers unless essential |
| playlist | User's playlist library | id, owner_id nullable for local-only, name, source_type, created_at, updated_at, is_active |
| playlist_source | Provenance and import record | id, playlist_id, source_kind (file/url), display_source, imported_at, content_hash, authorization_status, rights_reference, last_checked_at |
| channel | Normalized channel record | id, playlist_id, external_tvg_id, name, stream_uri, logo_uri, group_name, country_code, language_code, sort_order |
| category | Normalized category | id, name, normalized_name |
| channel_category | Many-to-many channel/category relation | channel_id, category_id; unique pair |
| favorite | Favorite channel relation | owner_id/device_id, channel_id, created_at; unique owner/channel pair |
| epg_source | XMLTV source metadata | id, owner_id, display_source, content_hash, imported_at, updated_at |
| epg_channel | XMLTV channel mapping | id, epg_source_id, external_channel_id, display_name, icon_uri |
| programme | EPG schedule item | id, epg_channel_id, title, description, start_at_utc, end_at_utc, category; end_at_utc > start_at_utc |
| channel_epg_mapping | Match app channel to EPG channel | channel_id, epg_channel_id, match_method, confidence; unique channel/source mapping |
| sync_state (future) | Incremental synchronization | owner_id/device_id, entity_type, cursor, last_synced_at |
| rights_record | Evidence for content use | id, source_id/channel_id, rights_holder, permitted_use, territories, valid_from, valid_until, evidence_uri, reviewed_at, status |
| playback_diagnostic (opt-in) | Minimal crash/quality telemetry | pseudonymous installation id, app_version, platform, error_code, occurred_at; no stream URL, tokens or viewing history by default |

### Required validation and indexes

- Unique playlist name per owner (case-insensitive); allow duplicate names across different owners.
- Unique external channel identifier only within its source/playlist unless a verified global identifier exists.
- Index channel by playlist_id, normalized name, country_code and group_name.
- Index programme by epg_channel_id and start_at_utc; reject invalid intervals.
- Enforce foreign keys and cascade rules explicitly; deleting a playlist must not delete a channel shared by another source.
- Validate all imported HTTP(S) URIs, reject embedded user-info and unsupported schemes. A public URL is not evidence of content rights.
- Never store raw credentials in stream URLs. Treat logos, EPG URLs and redirects as untrusted input.
- Keep raw imported files only when needed for re-import/debugging, enforce size limits, and provide a user-controlled delete/export path.

## 4. Local-first migration plan

1. Add a versioned SQLite schema and repository interfaces; keep UI code independent of the database implementation.
2. Add migrations with rollback-safe transactions and migration tests.
3. Import the existing JSON manifest, playlist files, legacy library files and favorites exactly once; use content hashes/idempotency keys to prevent duplicate imports.
4. Verify counts and content hashes before deleting or retiring legacy files. Never delete the old data on a failed or partial migration.
5. Add repository tests for create/read/update/delete, duplicate handling, interrupted writes, malformed records, migration from every supported schema version and large libraries.
6. Only after local persistence is stable, evaluate remote sync as a separate feature and threat-model it before implementation.

## 5. Secrets and keys: what exists and what must be supplied

No production secrets or signing keys are present or should be committed in this repository. Do not invent passwords, API keys, certificates or signing identities.

| Secret / key | Needed when | Owner action |
|---|---|---|
| Android upload keystore | Publishing a signed Android release | Owner creates/retains the keystore and backup securely |
| ANDROID_KEYSTORE_BASE64 | CI signing, if enabled | Owner stores base64 keystore bytes in GitHub Actions Secrets |
| ANDROID_KEYSTORE_PASSWORD | CI signing, if enabled | Owner creates a strong unique password and stores it as a secret |
| ANDROID_KEY_ALIAS | CI signing, if enabled | Owner supplies the alias from the keystore |
| ANDROID_KEY_PASSWORD | CI signing, if enabled | Owner supplies the key password |
| Backend service credentials | Only after a backend is selected | Owner provisions least-privilege server-side credentials |
| Third-party API keys | Only when an actual provider integration is selected | Owner creates keys in provider console; server-only keys stay server-side |
| OAuth client IDs / redirect URIs | Only if account login is implemented | Owner registers exact app identifiers and redirect URIs with provider |

GitHub Secrets are not readable through the repository content API and must never be requested in chat. The app must not contain a database administrator password, service-role key, private signing key, or unrestricted backend token. Public OAuth client IDs and public app configuration are not secrets, but still require correct platform restrictions.

### Owner setup path for Android signing (not yet performed)

1. Decide the permanent Android application ID and signing identity before the first public release.
2. Create an upload keystore locally using Android Studio/keytool on a trusted computer; keep two secure backups offline.
3. Never send the keystore or passwords in chat, commit them, or upload them as ordinary repository files.
4. In GitHub, open **Settings → Secrets and variables → Actions → New repository secret** and add the exact names above only after CI signing is implemented.
5. Ask for a dedicated PR to add a signing workflow that reads secrets only from the protected Actions environment and never prints them.
6. If a key is lost or exposed, stop release signing and follow the relevant platform key-reset/rotation process.

The current CI produces a debug APK only; debug signing is generated by the Android build environment and is not a production signing setup.

## 6. Privacy, security and operational requirements

- Data minimization: no account required for local playlist playback.
- Encryption: use platform-backed secure storage for tokens/credentials; encrypt sensitive server data at rest where appropriate.
- Transport: HTTPS/TLS for every remote API; reject cleartext production endpoints.
- Authorization: enforce ownership on every server-side read/write; never trust a client-supplied user_id.
- Import safety: size limits, timeouts, redirect limits, URI validation and private-network/SSRF protections for any future URL fetcher.
- Logging: redact tokens, passwords, full stream URLs and personal identifiers.
- Lifecycle: provide export/delete controls and retention periods before adding accounts or telemetry.
- Rights: record source provenance and evidence for owned/public-domain/licensed streams; territory and expiry must be enforceable.
- Operations: backups, restore drills, migrations, monitoring, incident response and key rotation are release requirements for a hosted service.

## 7. Decisions required from the owner before a cloud database is provisioned

- Is the first release strictly local/offline, or must users sign in and synchronize playlists across devices?
- If cloud sync is required: who owns/operates the backend, what budget and region are approved, and what privacy/retention policy applies?
- Which content sources have documented rights for the intended territories?
- What permanent Android application ID and release signing identity should be used?

Until these decisions are made, implement the local database abstraction and schema only; do not provision paid infrastructure or create production credentials.

## 8. Acceptance checklist

- [ ] Versioned local schema and migrations implemented.
- [ ] Existing JSON/files/preferences migrated without data loss.
- [ ] Repository and migration tests pass in CI.
- [ ] Playlist/channel/EPG relations and indexes verified with realistic datasets.
- [ ] Export/delete and privacy controls tested.
- [ ] Rights provenance recorded for every bundled or remotely catalogued stream.
- [ ] No secrets in source, build logs, artifacts or client bundle.
- [ ] Cloud backend and account model separately approved and threat-modelled, if needed.
- [ ] Release signing configured from owner-provided GitHub Secrets, not generated or guessed by an assistant.
